1. ФИЗИЧЕСКАЯ СУТЬ ПРОБЛЕМЫ: ПОЧЕМУ RGB ПОРОЖДАЕТ ЛОЖНЫЕ ТОЧКИ
================================================================================
Когда мы берем два кадра с разных камер и начинаем сравнивать пиксели по цветам
[R, G, B] (или нормализованную корреляцию по цветам), вступают в силу фундаментальные
законы оптики:

1. Неламбертово отражение (Non-Lambertian reflectance / блики):
   В Unreal Engine 5 освещение основано на физических шейдерах (Lumen/PBR).
   Камень, асфальт или капот машины отражают свет по функции BRDF. Камера 1
   видит отражение прямого солнечного луча (пиксель RGB = [230, 215, 180]),
   а Камера 2 под другим углом видит этот же камень в рассеянном свете
   (пиксель RGB = [85, 90, 75]). Разница по цвету огромна! Алгоритм решает,
   что это разные объекты, и ищет «желтоватый пиксель» где попало — например,
   цепляясь за кусок неба или светлое облако, создавая точку в воздухе.

2. Хроматическая аберрация и разница оптики:
   В проекте Peleng используются объективы с кардинально разным фокусным
   расстоянием (от 20 мм до 60 мм). На контрастных границах (хвоя елей на фоне неба,
   гребни гор) появляются цветные каемки разной ширины, порождающие ложные
   градиенты цвета.

3. Переход в ч/б (Grayscale):
   Интенсивность серого рассчитывается по стандарту ITU-R BT.601:
       Y = 0.2989 * R + 0.5870 * G + 0.1140 * B
   Однако простое сравнение ч/б яркостей (|Y1 - Y2|) также уязвимо к разнице
   экспозиции и теням. Требуется переход от абсолютной яркости к *топологии*.

2. МАТЕМАТИЧЕСКАЯ ФОРМУЛИРОВКА: ПРЕОБРАЗОВАНИЕ ЦЕНЗУСА (CENSUS TRANSFORM)
================================================================================
Преобразование Цензуса (Zabih & Woodfill, ECCV 1994) — это непараметрический
метод, который кодирует локальную структуру окрестности пикселя независимо от
абсолютного уровня освещения.

Формальное определение:
Пусть p = (u, v) — центральный пиксель, а N(p) — прямоугольное окно размера
(2r_u + 1) x (2r_v + 1) вокруг него (типично 7x7 или 9x7).
Преобразование Цензуса T(p) формирует битовую строку:
    T(p) = BIG_CONCATENATE_{q in N(p) \ {p}} xi(I(p), I(q))

где бинарная функция сравнения xi определяется как:
    xi(I(p), I(q)) = 1, если I(q) < I(p)
                     0, в противном случае

Физический смысл:
Нас не интересует, равен ли пиксель 200 или 40. Нас интересует только форма
рельефа яркости: кто из соседей темнее центра, а кто светлее.
Если на сцену упадет тень или одна камера затемнит кадр в 2 раза, отношения
«темнее/светлее» между соседними точками камня или ветки останутся неизменными.
Битовая строка T(p) инвариантна к монотонным изменениям яркости!

Метрика сходства — Расстояние Хэмминга (Hamming Distance):
Для сравнения пикселя p1 на левом кадре и p2 на правом кадре вычисляется
побитовое исключающее ИЛИ (XOR) и подсчитывается число единиц:
    Cost(p1, p2) = popcount( T_left(p1) ^ T_right(p2) )

Для окна 7x7 длина битовой строки равна 48 бит (помещается в один 64-битный uint64).
Расстояние Хэмминга вычисляется за 1 такт процессора инструкции __builtin_popcountll.

3. ПОШАГОВЫЙ ПАЙПЛАЙН РЕКОНСТРУКЦИИ ДВУХ КАМЕР (С ПРИМЕРОМ)
================================================================================
Пусть даны Камера 1 и Камера 2 с матрицами проекции P1 = K1 [R1 | t1] и P2 = K2 [R2 | t2].

ШАГ 1: Предобработка
1. Конвертация кадров RGB -> Grayscale (uint8).
2. Вычисление карт Цензуса CensusMap1 и CensusMap2 (uint64 на каждый пиксель).

ШАГ 2: Эпиполярное проецирование (Epipolar Ray Casting)
Для каждого выбранного пикселя p1 = (u1, v1) в Камере 1:
1. Вычисляется единичный оптический луч в мировых координатах:
       v1 = R1^T * K1^-1 * [u1, v1, 1]^T,  d1 = v1 / ||v1||
2. Луч в мире параметризуется глубиной lambda (в метрах):
       X(lambda) = C1 + lambda * d1
3. Ограничиваем lambda физическим коридором высоты [Z_min, Z_max]:
       lambda_min = (Z_min - C1_z) / d1_z
       lambda_max = (Z_max - C1_z) / d1_z
4. Проецируем отрезок луча [lambda_min, lambda_max] в Камеру 2:
       [u2(lambda), v2(lambda), w2(lambda)]^T = P2 * [X(lambda); 1]
       p2(lambda) = (u2 / w2, v2 / w2)
   Это дает строго отрезок эпиполярной линии на Камере 2.

ШАГ 3: Вычисление функции стоимости и поиск минимума
Идем вдоль отрезка с шагом 0.5–1.0 пикселя:
    Cost(lambda) = popcount( Census1(u1, v1) ^ Census2(u2(lambda), v2(lambda)) )

ШАГ 4: Три строгих фильтра против ложных точек (Фильтры валидности)
1. Фильтр абсолютного соответствия:
   Минимальная стоимость Cost_min <= 0.20 * NumBits (не более 20% несовпадающих бит).
2. Фильтр уникальности (Uniqueness Ratio):
   Пусть Cost_min — лучший минимум, а Cost_sec — второй локальный минимум
   на удалении более 3 пикселей. Требуем:
       Cost_min / Cost_sec < 0.75
   Если отношение >= 0.75, значит, на луче две похожие текстуры — точка бракуется!
3. Лево-правая проверка (Left-Right Consistency Check):
   Берем найденный пиксель p2 на Камере 2 и пускаем луч обратно в Камеру 1.
   Если обратный поиск нашел пиксель p1_back и ||p1 - p1_back|| > 1.0 пикселя —
   точка объявляется ложной и удаляется.

ШАГ 5: SVD-триангуляция
Если точка прошла все три фильтра, решается система DLT A * X = 0 через SVD,
давая чистую 3D-координату [X, Y, Z].

--- ПРИМЕР РЕАЛИЗАЦИИ НА PYTHON (ЧИСТЫЙ NUMPY / OPENCV) ---
```python
import numpy as np
import cv2

def compute_census_7x7(gray: np.ndarray) -> np.ndarray:
    """Вычисляет 48-битный Census Transform для окна 7x7."""
    h, w = gray.shape
    census = np.zeros((h, w), dtype=np.uint64)
    # Смещение по окрестности 7x7 (радиус 3)
    offsets = [(dr, dc) for dr in range(-3, 4) for dc in range(-3, 4) if not (dr == 0 and dc == 0)]
    
    for bit_idx, (dr, dc) in enumerate(offsets):
        # Сдвиг изображения для векторного сравнения
        r_src = slice(max(0, dr), min(h, h + dr))
        r_dst = slice(max(0, -dr), min(h, h - dr))
        c_src = slice(max(0, dc), min(w, w + dc))
        c_dst = slice(max(0, -dc), min(w, w - dc))
        
        diff = np.zeros((h, w), dtype=bool)
        diff[r_dst, c_dst] = gray[r_dst, c_dst] > gray[r_src, c_src]
        census |= (diff.astype(np.uint64) << np.uint64(bit_idx))
        
    return census

def hamming_cost(census1: np.uint64, census2: np.uint64) -> int:
    """Вычисляет расстояние Хэмминга между двумя 64-битными кодами."""
    xor_val = int(census1 ^ census2)
    return bin(xor_val).count('1')
```

4. БЕСПРИСТРАСТНЫЙ ИНЖЕНЕРНЫЙ АУДИТ: ПОЧЕМУ ЭТО МОЖЕТ НЕ СРАБОТАТЬ?
================================================================================
Ты задал ключевой вопрос: «Почему всё, что звучит идеально на словах, в итоге
ломается на практике?»
Вот честные, физические и математические причины, почему данный алгоритм
может давать сбой конкретно в вашем сценарии:

ПРИЧИНА 1: Угол расхождения лучей (Baseline Angle / Наклонные поверхности)
Преобразование Цензуса предполагает, что локальный узор окрестности 7x7
выглядит *одинаково* в обеих камерах.
Но если Камера 2 стоит на холме слева (X = -457 м), а Камера 4 на холме справа
(X = +332 м), угол между их лучами составляет около 160° (они смотрят НАВСТРЕЧУ
друг другу!).
Склон горы, обращенный к Камере 2, виден ей фронтально. А для Камеры 4 этот же
склон виден под острым скользящим углом 10° или вовсе скрыт за гребнем.
Окно 7x7 пикселей в Камере 1 из-за перспективы сжимается в полоску 7x1 пикселей
в Камере 2! Узор окрестности нарушается, и расстояние Хэмминга дает ложный минимум.
*Вывод*: Нельзя сопоставлять камеры, смотрящие навстречу друг другу. Базисный
угол между камерами должен быть в диапазоне 15°–60°.

ПРИЧИНА 2: Проблема апертуры (Aperture Problem / Однородный асфальт и склон)
Если окно 7x7 попадает на монотонный асфальт дороги или однотонную текстуру
травы/скалы без явных пятен, то внутри окна почти все пиксели имеют одинаковое
значение (разница на уровне цифрового шума).
В этом случае битовая строка Census вырождается в случайный шум или череду нулей.
Функция стоимости Cost(lambda) становится плоской «ванной» без выраженного минимума.
Алгоритм начинает цепляться за шум рендеринга Unreal Engine.

ПРИЧИНА 3: Ошибка калибровки в 0.5 градуса (Катастрофа эпиполярного выравнивания)
В стереозрении поиск ведется *строго вдоль одномерной эпиполярной линии*.
Толщина линии — ровно 1 пиксель.
Если в файле калибровки угол поворота камеры (Pitch или Roll) ошибается всего
на 0.2°–0.5° (что часто бывает при небрежном экспорте из симулятора), истинная
точка на Камере 2 смещается по вертикали на 4–8 пикселей В СТОРОНУ от
эпиполярной линии!
В итоге луч ищет точку там, где ее физически нет. И алгоритм либо не находит ничего,
либо находит случайный похожий куст на соседней строке, создавая дикую ошибку
по дальности в 50–100 метров!

ПРИЧИНА 4: Разрешение на дальних дистанциях (Pixel Footprint)
При фокусном расстоянии 35 мм и матрице Full HD 1920x1080 один пиксель на дальности
100 метров покрывает пятно размером 4 см на местности.
Но на дальности 400 метров один пиксель покрывает уже 16 см!
Любая ошибка сопоставления всего в 1 пиксель на дальности 400 метров дает
продольную ошибку глубины:
    Delta_Depth = (Z^2 / (f * Baseline)) * Delta_disp ≈ 8–15 метров!
Это фундаментальное физическое ограничение оптики: стереобазис не может
дать миллиметровую точность на полукилометровом удалении.

- Cam 2 (60mm): Loc=(-457m,  -65m, +79m), Rot=(0°,  -10°,    0°) -> Смотрит вдоль долины
- Cam 3 (35mm): Loc=(+126m, -227m, +14m), Rot=(0°,   -3°, +115°) -> Смотрит снизу вверх

Анализ пар:
- ПАРА Cam 1 + Cam 2: Базис отличный, угол схождения ~70°, идеально для начала дороги (кадры 0–190).
- ПАРА Cam 2 + Cam 4: КАТАСТРОФА ДЛЯ СТЕРЕО. Угол 160° (встречные камеры). Сопоставлять их напрямую по Census нельзя — они видят противоположные стороны одних и тех же деревьев и гор!
- ПАРА Cam 3 + Cam 5: Отличная стереопара для центральной части дороги (кадры 400–700).
- ПАРА Cam 4 + Cam 5: Хорошая стереопара для серпантина и подъема (кадры 700–1000).

6. НЕОБХОДИМЫЕ ПРЕДОХРАНИТЕЛИ: ЧТОБЫ ВСЁ РЕАЛЬНО РАБОТАЛО
================================================================================
Чтобы система перестала плодить ложные точки, в код внедряются 4 строгих правила:

1. Сопоставлять ТОЛЬКО согласованные пары камер:
   Стереопары делятся по секторам долины. Cam 2 сопоставляется только с Cam 1.
   Cam 4 сопоставляется только с Cam 5. Встречные камеры никогда не сопоставляются впрямую.

2. Двусторонний поиск полосы (Epipolar Band, а не Line):
   Чтобы исключить влияние мелких погрешностей калибровки симулятора, поиск ведется
   не по математической линии толщиной в 1 пиксель, а по узкой полосе шириной
   ±1.5 пикселя с последующим параболическим субпиксельным уточнением.

3. Ограничение по высоте дна долины Z_road(s):
   Вместо поиска по всей глубине от 10 м до 1000 м, глубина каждого луча жестко
   привязывается к высоте полотна дороги Z_road в данном секторе:
       Z_terrain in [Z_road(s) - 0.5m,  Z_road(s) + H_max(s)]
   Это сразу отсекает 100% точек, пытающихся появиться под землей или улететь в стратосферу.

4. Отбраковка сомнительных точек (Better No Point than Bad Point):
   Если точка не прошла Uniqueness Ratio < 0.75 или Left-Right Check, алгоритм
   НЕ ПЫТАЕТСЯ угадать ее положение. Пиксель помечается как «неопределенный»,
   а пропуск гладко затягивается интерполяцией Делоне от соседних подтвержденных точек.
